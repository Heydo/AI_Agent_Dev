00 / 全景

一张图看懂：一个仓库，三个包，两个进程

这个仓库不是"一个项目"，而是三个独立包被同一个根目录管理。根目录只负责调度， 真正干活的是 clients、services、packages 里各自的 package.json。

🖥️

clients/ · 客户端应用

面向用户的界面，最终被浏览器下载执行。这里是 chat-web：Next.js + React，开发端口 3002。

产物是 HTML / JS / CSS，用户看得见。

🧠

services/ · 服务进程

长期驻留在服务器上的进程，对外提供 API。这里是 chat：NestJS，端口 4001。

产物是"一直在跑"的进程，用户看不见。

🔗

packages/ · 共享子包

不属于任何一端、但两端都要用的代码。这里是 contracts：放 APP_NAME 这类契约。

产物是被别人 import 的源码 / 类型。

🚀 启动链路（一条命令起两个进程）

bun run dev → clean:ports → turbo run dev
@autix/chat → :4001 → wait-on → chat-web :3002
▶ 完整时序在 11 · 启动链路，可以点播放。

🌐 请求链路（点一次按钮发生了什么）

页面按钮 → fetch → GET :4001/hello → Nest
contracts → JSON → setState → 重渲染
▶ 可以亲手触发一次：12 · 请求链路。
💡
关键认知：clients 和 services 互相不 import。 它们只共享 contracts 这个包，彼此之间只通过 HTTP 说话。前端不知道后端是 Nest 还是 Express， 后端也不知道前端是 Next 还是 Vue——这条边界，就是"前后端分离"在代码层面的样子。

每个目录，都是一个独立的包

点左边任意一个节点，右边会告诉你：它是什么、里面有什么、为什么放在这一层。

AI_Agent_Dev/

仓库根目录

只负责"怎么把三个包一起跑起来"，自己不含业务代码。根 package.json 是调度台，workspaces 字段把三个目录纳入同一个依赖图。

  • package.json：脚本、workspaces、包管理器版本
  • turbo.json：任务编排规则

  • tsconfig.base.json：共享的 TS 编译选项与路径别名
02 / Monorepo 与 Workspaces

为什么不是三个 repo，而是三个目录？

monorepo 不是为了"看起来高级"。它解决的是：改一个共享常量，要在三个仓库里各改一遍、发三个版本、等三次 CI 的痛苦。

🧩

共享代码零发布

改 contracts 里的 APP_NAME，前端和后端下一次编译立刻拿到新值，不需要 npm publish。

🔒

依赖版本只有一个真相

根目录的 bun.lock 锁住整个图。Next / React / Nest 的版本在三个包里不会各说各话。

⚛️

一次改动 = 一次提交

契约、复用方、调用方在同一个 commit 里，review 时能看到完整影响面。

workspaces：把目录变成包

根 package.json 里的三个 glob，就是"包"的发现规则：

"workspaces": [
  "clients/*",
  "services/*",
  "packages/*"
]

每个匹配到的目录里必须有 package.json，且 name 唯一：@autix/chat-web、@autix/chat、@autix/contracts。

workspace:* 是什么？

chat-web 和 chat 在 dependencies 里写：

"@autix/contracts": "workspace:*"

意思是"用仓库里的那一份，不要从 npm 下载"。Bun 安装时会把它软链到本地目录，所以改源码立即生效。

改 contracts → 两个包同时看到
🧭
命名即边界：@autix/ 是作用域。它让 workspace 里的包一眼可辨，也避免了"客户端包名少写作用域导致 Turbo filter 找不到包"这种坑（真实踩过，见 13 · 踩坑档案）。
03 / 根 package.json

整个仓库的"调度台"

点左边的字段或右边的按钮，下面会解释这个字段为什么存在。根 package.json 里没有一行业务代码，全是"怎么协作"。 

"name": "root",
"private": true,
"workspaces": ["clients/*", "services/*", "packages/*"],
"packageManager": "bun@1.4.4",
"scripts": {
  "clean:ports": "for port in 3002 4001; do ... done",
  "dev": "bun run clean:ports && turbo run dev --parallel --filter=@autix/chat --filter=@autix/chat-web",
  "dev:chat-web": "turbo run dev --filter=@autix/chat-web",
  "dev:chat": "turbo run dev --filter=@autix/chat",
  "build": "turbo run build",
  "typecheck": "turbo run typecheck",
  "lint": "turbo run lint"
},
"devDependencies": {
  "turbo": "^2.8.20",
  "wait-on": "^9.0.5"
}

name: "root"

根包名

根包也是 workspace 里的一个包，但它 private: true，永远不会被发布。它不产出任何代码，只承载脚本与依赖管理。

为什么重要：没有它，根目录就只是一个文件夹，而不是 workspace 图里的节点。

脚本逐个拆

7 个脚本，各自解决一个问题

🧹 clean:ports ▸

开发时最烦的事之一：上次进程没关干净，3002 / 4001 被占，下次启动直接 EADDRINUSE。

它用 lsof -ti :端口 找到占用进程，kill -9 强杀。写在 dev 前面，每次启动先清场。

只适合本地开发——生产环境千万别这么干。

🚀 dev ▸

clean:ports && turbo run dev --parallel --filter=@autix/chat --filter=@autix/chat-web

先清端口，再让 Turbo 同时启动两个 dev 任务。--parallel 表示不等任务依赖，两个进程并行启动；--filter 只启动这两个包。

注意：--parallel 在 Turbo 2.x 已标记 deprecated；更推荐用 turbo.json 的 persistent: true 表达长驻任务。

🧩 dev:chat / dev:chat-web ▸

单独启动某一个进程。排查问题时非常有用：先用 bun run dev:chat 确认后端能起来，再起前端。

--filter=@autix/chat 严格按包名匹配——名字写错一个字符就会报 "No package found"。

📦 build / typecheck / lint ▸

三个都是 turbo run <task>：Turbo 会到每个包里找同名脚本，按 turbo.json 的依赖关系执行，并尽可能复用缓存。

注意：如果某个包没有对应脚本，它不会报错，只会"跳过"——所以会出现 "Tasks: 0 successful" 的假成功。

🔌 packageManager ▸

"packageManager": "bun@1.4.4" 是给 Corepack / Turbo / 编辑器看的"版本声明"：这个仓库用哪个包管理器、哪个版本。

它不是自动安装，但能让 Turbo 判断该用哪个锁文件、怎么执行脚本。

🛠 devDependencies: turbo + wait-on ▸

turbo：任务编排器，根脚本里所有 turbo run 都靠它。

wait-on：等某个端口 / URL 就绪。本仓库里它其实写在了 chat-web 的 dev 脚本里（wait-on tcp:4001），根目录这份是历史遗留。

📝
为什么不给 package.json 写注释？ JSON 标准不支持注释。Bun 会把 package.json 当 JSONC 解析（能读 // 和尾逗号）， 但 Turbo 严格按 JSON 解析——实测 Turbo 2.8 / 2.11 都会在读到注释时报 package_json_parse_error。
turbo · 注释演示
× Unable to parse package.json.
Expected a property but instead found '// The root of the monorepo'.
→ 注释说明只能放在独立文档里，这也是 README 和本页面存在的原因。
04 / Turborepo

它不是打包器，是任务编排器

Turbo 自己不编译任何代码。它做的事只有四件：看懂包图、看懂任务图、并行调度、给结果做缓存。 下面这个模拟会真的"跑"一次构建——点按钮试试。

🗺️

包图

从 workspaces 读出三个包和它们的依赖关系。

🧾

任务图

读 turbo.json，知道 build 依赖 ^build（上游包的 build）。

⚡

并行调度

没有依赖关系的任务同时开跑，有依赖的按序执行。

💾

缓存

输入没变时直接回放结果，第二次构建通常不到 0.1s。

点击上面的按钮，看 Turbo 怎么调度这三个包。

turbo.json：只写"任务规则"

{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "dev": {
      "dependsOn": ["^build"],
      "cache": false,
      "persistent": true
    },
    "typecheck": { "dependsOn": ["^typecheck"] }
  }
}

"^build"

先跑"我依赖的包"的 build，再跑我的。这就是任务图。

outputs

告诉 Turbo 哪些目录算产物，缓存时要保存它们。

persistent: true

dev 是长驻进程，不会退出。Turbo 需要知道这一点，才不会等它"结束"。

cache: false

dev 的结果是"一直在跑"，没有可缓存的产物，缓存反而会阻止启动。

⚠️
三个真实踩过的 Turbo 坑： ① turbo.json 是 0 字节空文件时，任何命令都直接解析失败；② 任务在 turbo.json 里声明了、但没有包实现对应脚本时，会得到 "Tasks: 0 successful"； ③ --filter 严格按包名匹配，包名少写作用域直接导致 dev 起不来。
05 / 依赖安装 · isolated linker

node_modules 不是一坨，而是一个仓库

bunfig.toml 里只有一行：linker = "isolated"。它改变了"依赖装在哪、谁能看到谁"。 切换下面的开关看看区别。

isolated · 每个包只看见自己声明的依赖（当前）

hoisted（传统 npm / pnpm 默认类似）

依赖尽量提升到根 node_modules，谁都看得见
node_modules/ ├── next/ ├── react/ ├── @autix/contracts → ../../../packages/contracts └── turbo/ clients/chat-web/node_modules/ └── （可能是空的） ⚠ 幽灵依赖：不声明也能 require('next')
后果
  • 看着方便，但依赖关系被隐藏
  • 删掉一个依赖，别的包可能突然崩
  • 升级/迁移时很难判断"到底谁在用"

isolated（本仓库的真实选择）

实体依赖藏在 .bun 存储，按声明逐包软链
node_modules/ ├── .bun/（依赖实体） ├── turbo → .bun/turbo@… └── wait-on → .bun/wait-on@… clients/chat-web/node_modules/ ├── @autix/contracts → ../../../../packages/contracts └── next → .bun/next@16.4.5/… services/chat/node_modules/ ├── @autix/contracts → ../../../../packages/contracts └── .bin/nest
后果
  • 没声明的依赖 = 看不见（幽灵依赖消失）
  • workspace 间直接软链到源码目录
  • 改 contracts，两端立即生效
  • 新增依赖必须装到"使用它的那个包"
📌

依赖声明 = 可见性

在 isolated 下，想在 chat-web 里 use next，就必须在 chat-web 的 package.json 里声明 next。

🔗

workspace 就是软链

node_modules/@autix/contracts 指向 packages/contracts 源码目录，不是复制品。

🧱

锁文件只有一个

根目录 bun.lock 记录整个仓库的解析结果；子包不各存一份。

🧪
真实仓库里的证据：根 node_modules 只有 turbo / wait-on 的软链和 .bun 存储；chat-web 的 @autix/contracts 指向 ../../../../packages/contracts。这不是比喻，是 readlink 的真实输出。

✅

07 / TypeScript 边界

四份 tsconfig，各管一段编译

这个仓库有 tsconfig.base.json 和每个包自己的 tsconfig。点标签切换—— 重点是看"同一份配置，为什么在不同包里长得不一样"。 

{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022"],
    "paths": {
      "@autix/contracts": ["./packages/contracts/src/index.ts"],
      "@autix/contracts/*": ["./packages/contracts/src/*"]
    }
  }
}
🧭
只放"所有包都同意"的选项。target 决定语法降到哪个年代；paths 是给编辑器和 tsc 的"路径别名"——它不是 Node 的解析规则，运行时还得靠 workspace 软链。
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "target": "ES2017",
    "lib": ["dom", "dom.iterable", "esnext"],
    "module": "esnext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "noEmit": true,
    "strict": true,
    "paths": { "@/*": ["./src/*"] }
  }
}
🖥️
前端只做类型检查，不产出 JS。真正把 JSX / TS 变成浏览器代码的是 Next（SWC / Turbopack），所以这里 noEmit: true；moduleResolution: bundler 允许无扩展名 import 和 exports 字段解析。
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "outDir": "./dist",
    "rootDir": "./src",
    "declaration": true
  },
  "include": ["src"]
}
🧱
tsconfig 给"未来"准备的。当前它并不产出 dist（package.json 直接指向 src）；但只要需要构建，rootDir: ./src + outDir: ./dist 就保证产物结构是 dist/index.js。
{
  "module": "nodenext",
  "moduleResolution": "nodenext",
  "target": "ES2023",
  "experimentalDecorators": true,
  "emitDecoratorMetadata": true,
  "types": ["node", "jest"],
  "outDir": "./dist",
  "rootDir": "."
}
🧠
这是 Node 服务端，规则最"硬"。nodenext 严格遵循 Node 的模块解析；emitDecoratorMetadata 让装饰器把类型信息写进 metadata，Nest 的依赖注入才能知道"构造器要什么"。

装饰器 → 元数据 → 依赖注入

@Injectable()
标记可注入 → emitDecoratorMetadata → reflect-metadata
运行时读取 → Nest 容器
自动 new

所以 main.ts 第一行必须 import 'reflect-metadata'——没有它，容器读不到构造器的参数类型。

08 / 前端 · Next.js

next.config.ts 里的四行，每一行都在解决一个跨包问题

前端代码本身很薄：一个按钮、一次 fetch。真正有意思的是它怎么"看见" workspace 里另一个包的源码。

📦

transpilePackages

让 Next 把 @autix/contracts 的 TS 源码也一起编译，而不是当外部依赖跳过。

🚢

output: standalone

构建时把运行所需文件摊成一个可独立部署的目录，给后面的 Docker 用。

🧲

outputFileTracingRoot

monorepo 里依赖可能在仓库根部。告诉 Next "往上找到这里为止"，否则 standalone 会漏文件。

🔧

env

把 NEXT_PUBLIC_API_BASE_URL 注入构建，默认 http://localhost:4001。

NEXT_PUBLIC_ 到底是怎么进到浏览器里的？
构建期内联
保留 NEXT_PUBLIC_ 前缀（浏览器可读） 
// 点击"模拟 next build"，看构建产物里到底写了什么
浏览器里的 process.env.NEXT_PUBLIC_API_BASE_URL = 尚未构建

结论：NEXT_PUBLIC_ 不是运行时读取，而是构建时被替换成字符串字面量。所以改了值必须重新构建；也所以它不能放密钥。

page.tsx 只有三个动作

"use client";

export default function Home() {
  const [result, setResult] = useState("等待调用…");
  async function callApi() {
    const res = await fetch(
      `${process.env.NEXT_PUBLIC_API_BASE_URL}/hello`
    );
    const data = await res.json();
    setResult(data.message);
  }
  return <>
    <h1>{APP_NAME}</h1>
    <button onClick={callApi}>调用 API</button>
    <pre>{result}</pre>
  </>;
}

"use client"：这个组件需要状态和点击事件，必须在浏览器里执行。

wait-on tcp:4001

chat-web 的 dev 脚本先等后端端口就绪再启动 Next。否则页面能开，但第一次点击就 fetch 失败。

APP_NAME 从哪来？

直接 import { APP_NAME } from "@autix/contracts"。构建时被内联进前端 bundle，不是运行时请求。

跨域问题留给后端

浏览器访问 3002，API 在 4001，属于不同源。必须由 Nest 打开 CORS，前端不需要额外代理。

09 / 后端 · NestJS

五个文件，一条请求的完整生命周期

Nest 的代码看起来"绕"，是因为它把"谁负责什么"拆得很细：入口、模块、控制器、服务、契约。 点开每个文件，看看它只做哪一件事。

🚪 src/main.ts · 进程入口 ▸

建应用、开 CORS、监听 4001。它不认识任何业务逻辑，只负责"把 Nest 跑起来"。

import "reflect-metadata";
import { NestFactory } from "@nestjs/core";
import { AppModule } from "./app.module";

const app = await NestFactory.create(AppModule);
app.enableCors({
  origin: process.env.CORS_ORIGIN || "http://localhost:3002",
});
await app.listen(process.env.PORT ?? 4001);
📦 src/app.module.ts · 装配说明书 ▸

模块是 Nest 的"装配单元"：controllers 负责接请求，providers 负责提供逻辑，imports 负责引入别的模块。

@Module({
  imports: [],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}
🛎️ src/app.controller.ts · 路由分发 ▸

只负责"接住 HTTP 请求、把活交给 service"。构造器里注入 AppService，是 Nest 的依赖注入。

@Controller()
export class AppController {
  constructor(private readonly appService: AppService) {}

  @Get("health")
  getHealth() { return this.appService.getHealth(); }

  @Get("hello")
  getHello() { return this.appService.getHello(); }
}
🧠 src/app.service.ts · 业务逻辑 ▸

这里才出现 APP_NAME。业务逻辑与路由分离，控制器可以改、测试可以单独写。

@Injectable()
export class AppService {
  getHello() {
    return { message: `Hello from Chat, shared APP_NAME=${APP_NAME}` };
  }
  getHealth() { return { ok: true }; }
}
🔗 src/... · 它和 contracts 的关系 ▸

service 里 import { APP_NAME } from "@autix/contracts"。在 isolated 布局下，这个 import 被解析到根 node_modules 的软链，最终指向 packages/contracts/src/index.ts。

TypeScript 编译时会把它编进 dist；运行时不需要单独部署 contracts 包。

dev · nest start --watch

编译 + 启动 + 监听文件变化自动重启。开发时用。注意：这里包了一层 bun 启动 CLI。

build · nest build

只编译到 dist，不常驻。CI / 部署前用。同样包了 bun。

start · bun run dist/main.js

直接跑编译产物，不再经过 CLI。生产启动用。

🐛
为什么 dev / build 要写 bun node_modules/.bin/nest？这是本项目对 Nest CLI 12 + Node 22.14 的 ESM 崩溃做的修复。原因在 10 · Bun vs Node，值得完整看一遍。
10 / Bun vs Node

"不是说用 Bun 吗，怎么又跟 Node 有关？"

这是整个学习过程中最反直觉的一次事故。Bun 不是"Node 的替代品"这么简单—— 它同时扮演安装器、脚本运行器、运行时和 npx 替代品四个角色，而其中一个角色默认会把工作交给 Node。

📥

安装器

bun install：读写 node_modules 和 bun.lock，用 isolated 布局。

📜

脚本运行器

bun run dev：执行 package.json scripts，按 PATH 找可执行文件。

⚙️

运行时

bun dist/main.js：直接执行 JS，等价于 node 的角色。

📦

npx 替代

bunx @nestjs/cli：临时下载并执行 npm 包的 bin。

🧵
关键规则：包里的可执行文件第一行通常写着 #!/usr/bin/env node。bunx 和 bun run 默认尊重这个 shebang—— 也就是说，bunx @nestjs/cli 用 Bun 下载 CLI，却用 Node 执行它。只有加 --bun 才会强制用 Bun 跑。

npm registry 的 latest 已经是 @nestjs/cli 12.0.11（教程写作时是 11），自动拉到 12。

🧾

13 / 踩坑档案

11 个真实踩过的坑，按类型筛选

这些不是"可能会遇到的问题"，而是这次学习实际卡住过的点。每条都给出：现象、本质、修法。

11 条
高 turbo.json 是 0 字节空文件 ▸

现象：bun run build 报 Unable to read repository configuration ... invalid JSON ... found the end of the file。

本质：Turbo 启动第一步就是读配置，空文件不是"默认配置"，而是解析失败。

修法：写入合法 JSON（至少 {"tasks": {}}），再按需补任务。

高 "Tasks: 0 successful" 的假成功 ▸

现象：bun run build 显示 Packages in scope、Running build in 1 package，但最后 Tasks: 0 successful, 0 total。

本质：turbo.json 声明了 build 任务，但唯一在 scope 里的包（contracts）没有 build 脚本，没有可执行的任务。

修法：给包加 scripts，或接受"这个包不需要构建"的事实。

低 --parallel 已弃用 ▸

现象：启动时出现 WARNING --parallel is deprecated and will be removed...。

本质：Turbo 2.x 推荐用 turbo.json 的 persistent: true 表达长驻任务，而不是命令行开关。

修法：可以去掉 --parallel；它不影响运行，只是噪音。

高 No package found with name '@autix/chat' ▸

现象：bun run dev 报 × No package found with name '@autix/chat' in workspace，直接退出。

本质：根 dev 脚本 filter 了 @autix/chat，但 services/chat 当时还没创建；同时客户端包名是 chat-web，缺 @autix/ 作用域。

修法：先创建服务端并把客户端包名改成 @autix/chat-web；或用 dev:chat-web 单独启动。

中 wait-on tcp:4001 一直等 ▸

现象：chat-web 的 dev 脚本卡在 wait-on tcp:4001，3002 一直打不开。

本质：前端 dev 依赖后端先起；后端没起或起不来，等待就是无限循环。

修法：先跑 bun run dev:chat 确认 4001 活着，再跑前端；排查后端日志。

高 bunx 拉到 Nest CLI 12 后直接崩 ▸

现象：bunx @nestjs/cli new services/chat 报 ERR_REQUIRE_CYCLE_MODULE，CLI 还没开始工作就退出。

本质：教程没锁 CLI 版本，latest 从 11 变成 12；CLI 12 的 Angular devkit 22 在 CommonJS 里 require 纯 ESM 的 ora 9，Node 22.14 的 require(esm) 循环检测抛错。而 bunx / bun run 默认尊重 bin 的 node shebang，用 Node 执行。

修法：CLI 前加 bun（见 10 · Bun vs Node），或换回 Nest 11 栈。

低 给 package.json 写注释 ▸

现象：加 // 注释后 Turbo 报 package_json_parse_error。

本质：JSON 标准不支持注释；Bun 能读 JSONC，但 Turbo 严格按 JSON 解析。

修法：注释放独立文档；turbo.json 倒是有 turbo.jsonc 可以写注释。

高 isolated 下的"幽灵依赖"消失 ▸

现象：在某个包里 import 一个没在它 package.json 里声明的依赖，本地能跑、换台机器 / 严格安装后就 Cannot find module。

本质：isolated linker 只把"声明过的依赖"软链给这个包；传统 hoisted 把依赖提到根 node_modules，谁都能碰到。

修法：谁用谁装：bun add <pkg> --filter @autix/chat-web（或手改该包 package.json 后 bun install）。

中 Node 直接 import contracts 的 .ts 源码 ▸

现象：import("@autix/contracts") 报 ERR_UNKNOWN_FILE_EXTENSION ".ts"；而 require() 却能拿到值。

本质：contracts 的 exports 指向 src/index.ts，是为了让 Next / ts-node 这类能处理 TS 的工具消费；裸 Node 不认 .ts（当前 Node 22.14 的 type stripping 未开启）。

修法：本章够用；生产环境给 contracts 加构建，exports 指向 dist。

中 教程版本漂移：bun / turbo / Next 全都更新了 ▸

现象：照着教程装出来的版本和教程截图不一致（bun 1.4.4 vs 1.3.11；Next 16.4.5 vs 16.2.3）。

本质：教程是某个时间点的快照，命令没锁版本就会漂移。

修法：先能跑通，再理解差异；关键命令写死版本（如 @nestjs/cli@11），或接受新版本并按报错修。

中 前端显示 undefined / 请求发到错误地址 ▸

现象：页面能开，但 fetch 的 URL 是 undefined/hello。

本质：NEXT_PUBLIC_API_BASE_URL 没注入（next.config 的 env 没写、或变量没加 NEXT_PUBLIC_ 前缀，浏览器拿不到）。

修法：在 next.config.ts 的 env 里提供默认值；确认变量名以 NEXT_PUBLIC_ 开头；改完重新 build/dev。

15 / 自检清单

15 个问题，能答上来才算真的懂了

先自己在脑子里回答，再点开看答案。看完全部 15 条，这一章就算过关了。

0 / 15 已展开
1. 为什么根 package.json 不写业务代码？▸
根包是调度台：管 workspaces、scripts、共享 devDependencies。业务代码放进 clients / services / packages，才能被独立开发、构建、部署。
2. workspaces 的三个 glob 做了什么？▸
告诉包管理器：这三个目录下的每个 package.json 都是一个 workspace 包，一起进同一张依赖图、共用根锁文件。
3. packageManager: "bun@1.4.4" 谁在用？▸
Corepack / Turbo / 编辑器。它声明仓库用哪个包管理器版本，Turbo 据此判断锁文件与执行方式。
4. clean:ports 为什么要存在？▸
防止上次 dev 进程残留占用 3002 / 4001，导致新进程 EADDRINUSE。本地开发专用，生产不可用。
5. dev 任务为什么 cache:false + persistent:true？▸
dev 是长驻进程，没有"完成"和"产物"，persistent:true 让 Turbo 知道要一直等；cache:false 避免缓存阻止它每次重新启动。
6. dependsOn: ["^build"] 的 ^ 是什么意思？▸
表示上游依赖包的 build 任务。即"先构建我依赖的包，再构建我"，这是 Turbo 任务图的核心语法。
7. 为什么 --filter=@autix/chat 会找不到包？▸
filter 严格按包名匹配。@autix/chat 当时不存在（services/chat 未创建），且客户端实际包名是 chat-web（缺作用域），所以直接报错退出。
8. isolated 与 hoisted 最大区别？▸
hoisted 把依赖尽量提到根，所有包都能"蹭"到（幽灵依赖）；isolated 只在包自己的 node_modules 里软链它声明过的依赖，没声明就看不见。
9. 为什么 package.json 不能写注释？▸
JSON 标准不允许。Bun 宽容（按 JSONC 解析），但 Turbo 严格按 JSON 解析，会在注释处报 package_json_parse_error。
10. contracts 的 exports / types 为什么指向 src/index.ts？▸
为了让 Next、ts-node 这类能处理 TS 的工具直接消费源码，省掉构建步骤（零构建）。代价是裸 Node 直接 import 会不认 .ts。
11. NEXT_PUBLIC_ 前缀的意义？▸
标记这个环境变量可以被内联进浏览器 bundle。没有这个前缀，Next 不会把它暴露给客户端，浏览器里就是 undefined。
12. outputFileTracingRoot 解决什么？▸
monorepo 里依赖可能提升到仓库根。standalone 打包时如果不把追踪范围扩大到仓库根，就会漏掉文件，容器里跑不起来。
13. CORS 是谁在拦截请求？▸
浏览器。请求其实到达了服务器，服务器也返回了 200；但响应缺少 Access-Control-Allow-Origin 时，浏览器拒绝把结果交给 JS。
14. 为什么 nest 的 dev/build 命令前要加 bun？▸
Nest CLI 12 在 Node 22.14 下因 ESM/CJS 循环 require 崩溃。用 Bun 执行 CLI 可绕过；CLI 启动的编译产物进程仍由 node 跑，不受影响。
15. 为什么改 contracts 后前端立即变、后端要重启？▸
前端由 Next dev server 监听源码并热更新；后端是 nest start --watch，改 .ts 后需要重新编译并重启进程才能生效。

## 0. 先建立整体印象

一句话：**这是一个用 Bun 管理依赖、用 Turborepo 编排任务、由 3 个 workspace 包组成、最终跑起 2 个进程（前端 :3002 + 后端 :4001）的 monorepo。**

```
AI_Agent_Dev/                      ← 仓库根（不是 git 仓库，见 §14）
├── clients/                       ← 客户端应用层
│   └── chat-web/                  ← @autix/chat-web   Next.js 16   浏览器 :3002
├── services/                      ← 服务进程层
│   └── chat/                      ← @autix/chat       NestJS 12    API :4001
├── packages/                      ← 共享子包层
│   └── contracts/                 ← @autix/contracts  共享常量/类型（APP_NAME、未来的 DTO）
├── infra/compose/                 ← 部署编排目录（2.8 才会用到）
├── bunfig.toml                    ← Bun 安装策略：isolated
├── turbo.json                     ← Turborepo 任务图/缓存边界
├── tsconfig.base.json             ← TypeScript 公共基线
├── package.json                   ← 根：workspaces 聚合 + 统一命令入口
├── bun.lock                       ← 全仓唯一锁文件
└── docs/第二章项目讲义.md          ← 你正在读的文件
```

依赖方向是**单向**的（这一点很重要，后面会反复用到）：

```
@autix/chat-web ──workspace:*──┐
                               ├──> @autix/contracts ──> zod（npm 依赖，本章未使用，预留）
@autix/chat     ──workspace:*──┘
```

两个业务包都依赖 contracts；contracts **不**依赖任何业务包，所以不会出现循环依赖。

先记住两个链路，整份讲义都是围绕它们展开的：

- **启动链路**：`bun run dev` → turbo → 同时启动 chat（:4001）和 chat-web（:3002，会等 4001 就绪）
- **请求链路**：浏览器 :3002 点按钮 → `fetch` 到 :4001/hello → Nest 返回 JSON → 页面渲染

## 1. 项目构成：一个仓库，三个包，两个进程

### 1.1 三层目录的职责

| 目录 | 包名 | 是什么 | 运行方式 |
| --- | --- | --- | --- |
| `clients/chat-web` | `@autix/chat-web` | 面向用户的 Web 应用（Next.js App Router） | `next dev --port 3002`，浏览器访问 |
| `services/chat` | `@autix/chat` | 后端 API 服务（NestJS + Express） | `nest start --watch`，监听 4001 |
| `packages/contracts` | `@autix/contracts` | 前后端共享的常量/类型契约 | 不单独运行，被上面两个包 import |

为什么要这么分？因为这三类东西的**生命周期不同**：

- 客户端：面向前端开发者，构建产物部署到浏览器/CDN，迭代快；
- 服务端：面向后端/运维，有自己的进程、端口、环境变量、部署方式；
- 共享包：只被引用，不独立部署，改了要同时影响两边（这正是"契约"的意义）。

`clients/`、`services/`、`packages/` 下的每个子目录都是一个**独立的 npm 包**（有 `package.json`、有唯一 `name`），由根 `package.json` 的 `workspaces` 统一管理。`infra/` 不参与依赖安装，是部署配置目录。

### 1.2 本章真正用到的源码文件（完整地图）

```
clients/chat-web/
  package.json          @autix/chat-web 的依赖、脚本
  next.config.ts         Next 的编译/运行配置（transpilePackages、env…）
  tsconfig.json          extends 根基线 + Next 专属编译选项
  src/app/page.tsx       "use client" 页面：显示 APP_NAME + 调 /hello
  src/app/layout.tsx     App Router 根布局（脚手架生成）
  src/app/globals.css    全局样式（Tailwind 入口）

services/chat/
  package.json          @autix/chat 的依赖、脚本（dev/build/start）
  nest-cli.json          Nest CLI 配置（sourceRoot、deleteOutDir）
  tsconfig.json          后端 TS 编译选项（装饰器元数据等）
  tsconfig.build.json    真正构建时用的 tsconfig（只含 src，排除测试）
  src/main.ts            入口：创建应用、开 CORS、监听 4001
  src/app.module.ts      根模块：声明 controllers 和 providers
  src/app.controller.ts  路由：GET /health、GET /hello
  src/app.service.ts     业务逻辑：返回 message（用到 contracts 的 APP_NAME）

packages/contracts/
  package.json          name + exports/types 指向 src/index.ts
  tsconfig.json         extends 根基线（预留未来编译 dist）
  src/index.ts          export const APP_NAME = "llm"
```

## 2. 为什么用 monorepo + Bun workspaces

### 2.1 三个独立仓库的痛点

如果 clients/services/packages 各建一个仓库：

- 改一个共享常量（比如 `APP_NAME`），要在 3 个仓库分别提交、发版、升级依赖；
- 前后端版本容易对不上（前端用 v1 契约、后端用 v2）；
- 装依赖、跑脚本、跑 CI 要重复配置 3 套。

monorepo 把"多包"放进"一个仓库"：

- 跨包改动能**原子提交**（一次 commit 前后端 + 契约同时更新）；
- 包之间用包名互相引用，不需要发布到 npm；
- 统一的安装策略、锁文件、任务命令（`bun run dev` 一把梭）。

代价是：依赖边界容易变松（幽灵依赖）、任务依赖容易乱（谁先构建？）——所以我们需要 **Bun 的 workspaces + isolated linker** 保证依赖边界，需要 **Turborepo** 编排任务顺序。

### 2.2 workspace 是怎么被识别的

根 `package.json`：

```json
{
  "name": "root",
  "private": true,
  "workspaces": ["clients/*", "services/*", "packages/*"],
  "packageManager": "bun@1.4.4"
}
```

`bun install` 时，Bun 扫描 `clients/*`、`services/*`、`packages/*` 下所有含 `package.json` 的目录，把它们的 `name` 注册成 **workspace 成员**。之后：

- 别的包写 `"@autix/contracts": "workspace:*"`，Bun 不会去 npm 下载，而是**软链到本地 `packages/contracts`**；
- 全仓只维护**一个** `bun.lock`；
- 根脚本可以用 `turbo --filter=<包名>` 精确找到某个成员。

`private: true` 表示根包不发布，只做聚合。

### 2.3 `workspace:*` 到底是什么

`workspace:*` 是"版本协议"：告诉 Bun"这个依赖用本地 workspace 里的同名包，版本随便"。安装后你会看到：

```
clients/chat-web/node_modules/@autix/contracts -> ../../../../packages/contracts
services/chat/node_modules/@autix/contracts     -> ../../../../packages/contracts
```

**它指向的是源码目录，不是某个构建产物。** 所以改 `packages/contracts/src/index.ts`，前端/后端立刻能看到变化（配合各自的 watch/hot reload）——这就是"共享契约"能零成本联调的原因。

### 2.4 单一锁文件 + packageManager

- `bun.lock`：记录整个仓库所有包最终解析到的精确版本。删掉它，安装结果可能完全不同；
- `packageManager: "bun@1.4.4"`：声明本仓库用哪个包管理器及其版本。Turborepo 靠这个字段（+ 锁文件）判断该用 bun 还是 npm/pnpm 来跑脚本，缺了可能触发 package manager check 报错。

教程里写的是 `bun@1.3.11`（写作时的版本），本机实际装的是 1.4.4，所以根字段也改成了 1.4.4——**字段写的是实际版本才有意义**，这也是"配置要跟着环境改"的第一个例子。

## 3. 根 `package.json`：全仓的控制面板

### 3.1 完整文件

```json
{
  "name": "root",
  "private": true,
  "workspaces": ["clients/*", "services/*", "packages/*"],
  "packageManager": "bun@1.4.4",
  "scripts": {
    "clean:ports": "for port in 3002 4001; do lsof -ti :$port | xargs kill -9 2>/dev/null; done; echo 'Ports cleaned'",
    "dev": "bun run clean:ports && turbo run dev --parallel --filter=@autix/chat --filter=@autix/chat-web",
    "dev:chat-web": "turbo run dev --filter=@autix/chat-web",
    "dev:chat": "turbo run dev --filter=@autix/chat",
    "build": "turbo run build",
    "typecheck": "turbo run typecheck",
    "lint": "turbo run lint"
  },
  "devDependencies": {
    "turbo": "^2.8.20",
    "wait-on": "^9.0.5"
  }
}
```

### 3.2 逐字段说明

| 配置 | 值 | 作用 | 不写会怎样 |
| --- | --- | --- | --- |
| `name` | `root` | 根包标识 | 无所谓，根不发布 |
| `private` | `true` | 禁止误发布 | 可能被 `npm publish` |
| `workspaces` | `clients/*` 等 | 声明哪些目录是 workspace 成员 | 子包无法互相本地引用 |
| `packageManager` | `bun@1.4.4` | 声明包管理器与版本 | Turbo 可能无法识别、安装器版本漂移 |
| `devDependencies` | `turbo`、`wait-on` | 根脚本自己用到的两个工具 | 根脚本找不到命令 |

注意最后一行：**根脚本用到的工具必须写在根 `devDependencies`**。因为 isolated 安装策略下，根 `node_modules` 里只会软链根 `package.json` 声明过的依赖（§5）。

### 3.3 `scripts` 逐个讲

**`clean:ports`**

```bash
for port in 3002 4001; do lsof -ti :$port | xargs kill -9; done
```

- `lsof -ti :3002`：列出占用 3002 端口的进程 PID（`-t` 只输出 PID，`-i` 网络连接）；
- `xargs kill -9`：杀掉这些进程；
- 为什么需要：开发服务器挂在后台、或上次 Ctrl+C 没退干净时，端口会被占用，新进程启动失败。这是本地开发脚本，依赖 macOS/Linux 的 `lsof`。

**`dev`**（最重要的一行）

```bash
bun run clean:ports && turbo run dev --parallel --filter=@autix/chat --filter=@autix/chat-web
```

拆开看：

1. `bun run clean:ports`：先清端口（`&&` 保证清完再继续）；
2. `turbo run dev`：让 Turbo 去跑各包的 `dev` 脚本（**不是**直接跑 `next dev`）；
3. `--filter=@autix/chat --filter=@autix/chat-web`：只选这两个包；
4. `--parallel`：让 Turbo 忽略任务依赖图，并行跑（详见 §4.7）。

**`dev:chat` / `dev:chat-web`**：只启动单个包，排错时最有用。后端起不来时先单独 `bun run dev:chat` 看日志。

**`build` / `typecheck` / `lint`**：`turbo run <任务名>`。任务名必须在 `turbo.json` 的 `tasks` 里声明过，否则 Turbo 直接报错。当前 `turbo.json` 没有声明 `lint`，所以根 `bun run lint` 现在会报 `Could not find task`（属于已知待办，见 §14）。

### 3.4 为什么这个文件里没有注释（真实经历）

JSON 标准不支持注释。本仓库最初的需求是"给根 `package.json` 的每项配置写说明"，我们试过两条路：

1. **写 `//` 注释**：Bun 1.2+ 确实把 `package.json` 当 JSONC 解析，`bun install`/`bun run` 都能跑；但 **Turborepo 用严格 JSON 解析根 `package.json`**，实测 turbo 2.8.20 / 2.11.10 都会报 `package.json` 解析失败（`package_json_parse_error: Expected a property but instead found '// ...'`）。也就是说，注释会让 `turbo` 直接罢工。
2. **用 `"//xxx": "说明"` 这样的键值当注释**：turbo 能解析（未知字段被忽略），但对其他工具不保证，且污染配置语义。

所以最终方案是：**`package.json` 保持标准 JSON，说明统一写进根目录 `README.md`**。你正在读的讲义和 `README.md` 承担了"注释"的职责。

> 这件事本身就是个工程原则：**配置文件是给工具读的，说明文档是给人读的**，不要为了人的可读性破坏工具的兼容性。

## 4. Turborepo：任务编排器，不是打包器

### 4.1 Turbo 解决什么问题

当仓库里包变多，会遇到：

- "构建顺序"：A 依赖 B，就要先构建 B 再构建 A；
- "重复执行"：每次全量跑所有包的 build/typecheck，很慢；
- "并行度"：互不相关的任务应该同时跑；
- "缓存"：输入没变就不该重跑，直接复用上次产物。

Turborepo 就是干这四件事的：它读取 workspace 的包依赖图 + `turbo.json` 里的任务定义，负责**调度、并行、缓存**。它不管你怎么打包（打包是 Next/Nest/tsc 的事）。

### 4.2 `turbo run dev` 的执行链路

```
1. 读根 package.json 的 workspaces → 建立包图
2. 读 turbo.json 的 tasks → 知道每个任务怎么跑、依赖谁
3. 应用 --filter、--parallel 等参数 → 确定本次要跑哪些包/任务
4. 对每个目标包，执行它 package.json 里同名的 scripts.xxx
5. 按 dependsOn 排序 / 并行 / 写缓存（若允许）
6. 汇总输出：Tasks: N successful, M total
```

所以 `turbo run dev --filter=@autix/chat` 等价于"去 `services/chat` 里执行 `bun run dev`"，只是被 Turbo 包了一层调度和日志。

### 4.3 `turbo.json` 逐项拆解

```json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "dev": {
      "dependsOn": ["^build"],
      "cache": false,
      "persistent": true
    },
    "typecheck": {
      "dependsOn": ["^typecheck"]
    }
  }
}
```

| 字段 | 含义 |
| --- | --- |
| `$schema` | 只是给编辑器/IDE 的补全提示，不参与运行 |
| `tasks.<name>` | 定义一个任务；任务名要和包里的 `scripts.<name>` 对上 |
| `dependsOn: ["^build"]` | `^` 表示"先跑**依赖包**的 build"。这里是说：本包的 build 之前，先构建它依赖的 workspace 包 |
| `outputs` | 声明这个任务产出哪些文件/目录（缓存命中时用来恢复） |
| `cache: false` | 该任务不写缓存（dev 是常驻进程，没有"完成"的概念） |
| `persistent: true` | 告诉 Turbo 这是长期运行的进程（不会被当成普通任务等它结束） |

对本章来说：`build` 任务在我们这里其实没什么活干——contracts 没有 build 脚本，真正会构建的是 chat（Nest）和 chat-web（Next）。

### 4.4 缓存原理：为什么 dev 不能缓存

Turbo 的缓存逻辑是：

1. 计算任务输入的 hash（源文件、依赖版本、配置、环境变量等）；
2. 若上次跑过相同 hash 且成功，且 `cache` 没被关闭 → 不执行，直接把上次的 `outputs` 恢复出来；
3. 否则真实执行，成功后将 `outputs` 存入本地缓存（默认在仓库的 `.turbo/cache`）。

- `build`/`typecheck` 是"输入 → 输出"的纯函数，适合缓存；
- `dev` 是常驻服务（不会退出），既没有明确"完成"，也不能恢复出"一个正在跑的进程"，所以必须 `cache: false`，同时用 `persistent: true` 告诉 Turbo 别等它"结束"。

### 4.5 踩坑 1：空 `turbo.json`（你遇到的第一个报错）

现象：

```
Unable to read repository configuration .../turbo.json: invalid JSON
... Expected an array, an object, or a literal but instead found the end of the file.
```

本质：`turbo.json` 是 **0 字节空文件**（文件没保存成功）。Turbo 在干任何事之前先读配置，空文件不是"没有配置"，而是"语法错误"。修法：保存成合法 JSON（我们最终写的就是 §4.3 这份）。

### 4.6 踩坑 2：`Tasks: 0 successful, 0 total`

现象：`bun run build` 不报错，但输出 `WARNING No tasks were executed as part of this run`。

本质：配置没问题，是 **scope 里没有包拥有 `build` 脚本**。当时 Turbo 只看到 `@autix/contracts` 一个包，而它的 `package.json` 没有 `scripts` 字段 → 0 个任务可跑。这不是错误，是"无事可做"。

修法（二选一）：

- 给 contracts 加脚本（教程后面那个 `tsc -p tsconfig.json`，需要把 typescript 装到 contracts 自己的 devDependencies）；
- 或者接受"contracts 不需要构建"，等 chat/chat-web 建好后再跑 build（本章就是这样）。

### 4.7 踩坑 3：`--parallel` 弃用警告

你启动 dev 时会看到：

```
WARNING  --parallel is deprecated and will be removed in a future major version.
```

`--parallel` 的含义是：**忽略任务依赖图，能并行就并行**。这和 Turbo 的调度逻辑（按 `dependsOn` 保证顺序）是冲突的。

- 它在 dev 场景里确实省事：Web 和 API 互不依赖，直接一起起；
- 但新版 Turbo 更推荐用 `turbo.json` 的 `persistent: true` 来描述常驻任务，并发控制用 `--concurrency`。教程写作时还没这变化，所以保留了 `--parallel`；
- 它还有一个副作用：**在 `--parallel` 下，`dev.dependsOn: ["^build"]` 不会生效**（依赖图被忽略了），所以"先构建依赖再起 dev"这类保证会失效。我们目前没有跨包构建需求，所以影响不大。

### 4.8 踩坑 4：`--filter` 找不到包

现象（你之前遇到的）：

```
× No package found with name '@autix/chat' in workspace
```

本质：

- `--filter=@autix/chat` 是**按包名精确匹配**，不是目录名、不是模糊匹配；
- 当时 `services/` 还是空的（`@autix/chat` 尚未创建），`clients/chat-web` 的包名还是 `chat-web`（少了 `@autix/` 作用域）；
- Turbo 解析 filter 失败后会**直接退出（exit 1）**，不是"跳过继续"。

修法：统一命名——客户端包改名 `@autix/chat-web`，服务端建包叫 `@autix/chat`，然后 `bun install` 让 workspace 软链/锁文件更新。这也解释了为什么整个仓库坚持 `@autix/*` 前缀：它让 filter、workspace 引用、包名可读性都一致。

> 如果你要"模糊匹配"，Turbo 支持 `--filter=@autix/*` 之类的通配，但精确过滤更安全（不会误启动别的包）。

### 4.9 Turbo 怎么知道用哪个包管理器

两个线索：根 `package.json` 的 `packageManager` 字段 + 锁文件（`bun.lock`）。所以 `packageManager` 不是装饰，缺了可能触发 Turbo 的包管理器检查失败。教程 2.4.2 专门强调过这一点。

## 5. `bunfig.toml`：isolated 安装策略的原理与后果

### 5.1 两种安装布局

**hoisted（Bun 默认，也是 npm/yarn 的风格）**：

```
node_modules/
├── next/                  ← 所有依赖尽量平铺到根
├── react/
├── @autix/
└── ...
```

所有子包共用根 `node_modules`，子包即使没声明 `next` 也能 `require('next')`——因为根目录有。这就是**幽灵依赖（phantom dependency）**：代码能跑，但依赖关系是假的，换台机器/换个包管理器就可能崩。

**isolated（本仓库选了它）**：

```
node_modules/
├── .bun/                                   ← 所有包的"真实存储"
│   ├── next@16.4.5+<hash>/node_modules/next/
│   ├── wait-on@9.5.1+<hash>/node_modules/wait-on/
│   └── ...
├── turbo -> .bun/turbo@2.11.10/node_modules/turbo      ← 根自己声明的依赖才软链到根
└── wait-on -> .bun/wait-on@9.5.1+<hash>/node_modules/wait-on

clients/chat-web/node_modules/
├── @autix/contracts -> ../../../../packages/contracts   ← workspace 包直接链源码
├── next -> ../../../node_modules/.bun/next@16.4.5+<hash>/node_modules/next
├── react -> ...
└── .bin/next  .bin/tsc  .bin/wait-on                     ← 本包声明的依赖的可执行文件

services/chat/node_modules/
├── @autix/contracts -> ../../../../packages/contracts
├── @nestjs/core -> ...
├── node_modules/.bin/nest  .bin/tsc  .bin/jest ...
```

规则：**每个包只能看到自己在 `package.json` 里声明过的依赖**。没声明就是找不到——这是"严格"，也是"可复现"。

### 5.2 我们仓库里的真实证据

你可以自己验证：

```bash
ls node_modules                       # 只有 .bin .bun 和根声明的 turbo、wait-on
ls node_modules/.bun | head           # 依赖实体都在这（800+ 个目录）
readlink clients/chat-web/node_modules/@autix/contracts
# -> ../../../../packages/contracts   （workspace 包直接链源码！）
readlink clients/chat-web/node_modules/next
# -> ../../../node_modules/.bun/next@16.4.5+.../node_modules/next
ls clients/chat-web/node_modules/.bin         # next tsc wait-on eslint ...
```

### 5.3 后果一：依赖必须声明在"使用它的包"里

- `clients/chat-web` 的 dev 脚本里用了 `wait-on`，所以 `wait-on` 必须写进 **chat-web 自己的** `devDependencies`；
- `services/chat` 的脚本里用了 `nest`，所以 `@nestjs/cli` 必须写进 chat 自己的 devDependencies；
- 根脚本里用了 `turbo`，所以 turbo 在根 `devDependencies`。

如果只在某处"随便装了一下"（比如根装了、子包没声明），isolated 模式下子包就是找不到——这是它比 hoisted 严格的地方，也是教程推荐它的原因：**尽早暴露隐式依赖**。

### 5.4 后果二：workspace 包直接软链源码

`@autix/contracts -> ../../../../packages/contracts` 指向的是**源码目录**。所以：

- 不需要先构建 contracts；
- 改 contracts 源码，Next 的 Hot Reload / Nest 的 watch 重启会直接生效；
- 但也意味着"contracts 的构建产物"这个概念在本章不存在（见 §6）。

### 5.5 代价

- 安装结果更复杂（`.bun` 里带 hash 的目录名）；
- 某些工具对软链/嵌套 `node_modules` 敏感（Next 的 `outputFileTracingRoot` 就是为此而设，见 §8.4）；
- 新增依赖后必须重新 `bun install`，软链和锁文件才会更新（改包名后尤其如此）。

## 6. `packages/contracts`：共享契约的"零构建"设计

### 6.1 三个文件

**`packages/contracts/package.json`**

```json
{
  "name": "@autix/contracts",
  "version": "0.0.0",
  "exports": "./src/index.ts",
  "types": "./src/index.ts",
  "dependencies": {
    "zod": "^3.23.8"
  }
}
```

**`packages/contracts/tsconfig.json`**

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "outDir": "./dist", "rootDir": "./src" },
  "include": ["src"]
}
```

**`packages/contracts/src/index.ts`**

```ts
export const APP_NAME = "llm";
```

### 6.2 `exports` / `types` 是什么

- `exports`：Node 的**包入口映射**。`import "@autix/contracts"` 时，解析器打开这里指定的文件（字符串简写等价于 `{".": "./src/index.ts"}`）。
- `types`：TypeScript 找类型声明的入口。这里也指向 `.ts` 源码，所以编辑器/tsc 直接读到源码类型。

这里的关键设计是：**入口直接指向 TypeScript 源码，而不是构建产物**。

### 6.3 为什么可以"零构建"

- 前端：Next 本来就要编译 TS，把 contracts 源码一起编译即可（靠 `transpilePackages`，§8.4）；
- 后端：Nest 的 `tsc` 编译时会把 contracts 当类型来源；运行时 `require("@autix/contracts")` 解析到源码文件，实测 Node 22.14 能加载（`node -e "require('@autix/contracts')"` → `{"APP_NAME":"llm"}`）。
- workspace 软链让两个包"看到"的 contracts 是同一份源码，改一处两边生效。

### 6.4 代价与边界（很重要）

这个设计是**教学简化**，不是生产标准形态：

- 它不是"所有环境都能跑"：实测 `import('@autix/contracts')`（原生 ESM `import()`）会报 `ERR_UNKNOWN_FILE_EXTENSION: Unknown file extension ".ts"`。也就是说，**CJS 侧能凑合，纯 ESM 侧不行**。Next 能跑是因为打包器在构建期就把它编译了；Nest 能跑是因为编译产物是 CJS。
- 生产环境的共享包一般会 **先构建**：`exports` 指向 `./dist/index.js` + `./dist/index.d.ts`，用发布/构建流程保证消费方拿到的是 JS。
- 后续 contracts 要放 zod schema、DTO 时，建议把 `@autix/contracts` 的 `build` 脚本（`tsc -p tsconfig.json`）补上，让 `bun run build` 真正构建它。

当前的 `zod` 依赖是教程预留的（本章代码还没用到），属于"先占坑"。

## 7. TypeScript 的编译边界：tsconfig 家族

### 7.1 `tsconfig.base.json`：公共基线

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022"],
    "paths": {
      "@autix/contracts": ["./packages/contracts/src/index.ts"],
      "@autix/contracts/*": ["./packages/contracts/src/*"]
    }
  }
}
```

- `target`/`lib`：编译目标语法与内置库；
- `paths`：路径别名，让 `import "@autix/contracts"` 在**类型层面**直接指到源码（编辑器跳转、类型检查都靠它）。

### 7.2 三个子包各自 extends

| 包 | tsconfig 特点 | 为什么 |
| --- | --- | --- |
| `clients/chat-web` | `moduleResolution: bundler`、`jsx: react-jsx`、`noEmit: true`、`plugins: [next]` | Next 自己负责编译，tsc 只做类型检查 |
| `packages/contracts` | `outDir: dist`、`rootDir: src` | 预留"未来编译成 dist"的边界 |
| `services/chat` | `module/moduleResolution: nodenext`、`emitDecoratorMetadata`、`outDir: dist`、`strict` | Nest 用 tsc 编译，且装饰器需要元数据 |

### 7.3 一个容易踩的细节：`paths` 会被整体覆盖

`extends` 只做**浅合并**：子配置里只要写了自己的 `paths`，就会**整体替换**父配置的 `paths`，不是逐条合并。

`clients/chat-web/tsconfig.json` 里写了：

```json
"paths": { "@/*": ["./src/*"] }
```

于是 base 里的 `@autix/contracts` 别名在这个包里**就没了**。那为什么前端还能 `import { APP_NAME } from "@autix/contracts"`？

- 因为 isolated 安装把 `@autix/contracts` 软链进了 `clients/chat-web/node_modules/`，模块解析走 `node_modules` 就能找到；
- 再加上 Next 的 `transpilePackages` 负责编译它。

所以别名和实际模块解析是两条路，真正保证能 import 的是**软链**。想彻底对齐的话，可以给 chat-web 的 paths 补上 contracts 条目，但当前没必要。

### 7.4 为什么 Nest 必须开 `emitDecoratorMetadata`

Nest 的依赖注入（DI）依赖**运行时元数据**：

```ts
@Controller()
export class AppController {
  constructor(private readonly appService: AppService) {}
```

Nest 容器要实例化 `AppController`，必须知道构造器参数 `appService` 的类型是 `AppService`。这个信息来自 TypeScript 编译器发射的 `design:paramtypes` 元数据——前提是：

- `experimentalDecorators: true`（支持装饰器语法本身）；
- `emitDecoratorMetadata: true`（额外发射类型元数据）；
- 入口 `main.ts` 第一行 `import 'reflect-metadata'`（提供元数据读写的运行时）。

少任何一个，Nest 启动时就会报 "Nest can't resolve dependencies" 之类的问题。这是 Nest 的 tsconfig 和普通前端项目最大的差别。

### 7.5 为什么 Nest 有 `tsconfig.build.json`

`tsconfig.json` 是给 IDE 用的（包含 src + test + spec 文件，`rootDir: "."`）；`tsconfig.build.json` 是给 `nest build` 用的：

```json
{
  "extends": "./tsconfig.json",
  "compilerOptions": { "rootDir": "./src" },
  "include": ["src"],
  "exclude": ["node_modules", "test", "dist", "**/*spec.ts"]
}
```

- 排除测试文件，避免它们被打进 `dist/`；
- `rootDir` 收紧到 `src`，保证编译产物结构是 `dist/main.js`（而不是 `dist/src/main.js`）；
- 构建前 `deleteOutDir`（nest-cli.json）清空旧 `dist`，避免残留文件。

## 8. `clients/chat-web`：Next 前端逐项讲解

### 8.1 它怎么来的 & 与教程的差异

用 `create-next-app` 生成（Next 16.4.5、React 19.3.0、App Router、Tailwind 4、ESLint 9、TypeScript）。

与教程的两处结构差异：

1. **路径**：教程写 `clients/chat-web/app/page.tsx`，实际是 `clients/chat-web/src/app/page.tsx`。新版脚手架默认带 `src/`，Next App Router 两种布局都支持（`src/app` 优先），代码不用改。
2. **包名/版本**：教程 2.5.1 要求 `name: "@autix/chat-web"`、`version: "0.0.0"`，你一开始漏改（还是 `chat-web` / `0.1.0`），后来改成 `@autix/chat-web`（版本保留 0.1.0）。这是根 `dev` 的 `--filter=@autix/chat-web` 能找到包的前提。

### 8.2 `package.json` 里值得懂的字段

```json
{
  "name": "@autix/chat-web",
  "version": "0.1.0",
  "private": true,
  "scripts": {
    "dev": "wait-on tcp:4001 && next dev --port 3002",
    "build": "next build",
    "start": "next start --port 3002",
    "typecheck": "tsc --noEmit",
    "lint": "tsc --noEmit"
  },
  "dependencies": {
    "@autix/contracts": "workspace:*",
    "next": "16.4.5",
    "react": "19.3.0",
    "react-dom": "19.3.0"
  },
  "devDependencies": {
    "@tailwindcss/turbopack": "^4",
    "@types/node": "^20",
    "@types/react": "^19",
    "@types/react-dom": "^19",
    "babel-plugin-react-compiler": "1.0.0",
    "eslint": "^9",
    "eslint-config-next": "16.4.5",
    "tailwindcss": "^4",
    "typescript": "^5",
    "wait-on": "^9.0.5"
  }
}
```

- `name`：必须和根脚本 filter 里的一致；
- `@autix/contracts: workspace:*`：本地软链（§2.3）；
- `dev`: `wait-on tcp:4001 && next dev --port 3002`
  - `wait-on tcp:4001`：轮询 4001 端口，直到后端可连接才继续；避免"前端起来了但后端还没起，一请求就报错"；
  - `next dev --port 3002`：固定端口，和 CORS 白名单、教程约定一致；
- `build` / `start`：生产构建与启动；
- `typecheck` / `lint`：本章都用 `tsc --noEmit` 占位（真正的 ESLint 校验留到以后）；
- `trustedDependencies` / `ignoreScripts`：新版 Bun 模板为 `sharp`、`unrs-resolver` 这类需要下载原生二进制的依赖加的白名单（Bun 默认不执行依赖的安装脚本，防止供应链攻击）。
- `@tailwindcss/turbopack`、`babel-plugin-react-compiler`：新版脚手架的默认产物，本章用不到，不影响链路。

### 8.3 `tsconfig.json`

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "target": "ES2017",
    "lib": ["dom", "dom.iterable", "esnext"],
    "strict": true,
    "noEmit": true,
    "module": "esnext",
    "moduleResolution": "bundler",
    "jsx": "react-jsx",
    "plugins": [{ "name": "next" }],
    "paths": { "@/*": ["./src/*"] }
  },
  "include": ["next-env.d.ts", "**/*.ts", "**/*.tsx", ".next/types/**/*.ts", ".next/dev/types/**/*.ts"]
}
```

- `moduleResolution: bundler`：按"打包器"的规则解析包（Next/webpack/Turbopack 使用），允许省略扩展名等；
- `noEmit: true`：tsc 只检查类型，不产出文件（真正编译是 Next 干的）；
- `plugins: [{ "name": "next" }]`：让编辑器获得 Next 的类型插件支持；
- `include` 里带 `.next/types`：Next 生成的类型（如路由类型）也要参与类型检查。

### 8.4 `next.config.ts`：前端最关键的三个配置

```ts
import path from "node:path";
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  transpilePackages: ["@autix/contracts"],
  output: "standalone",
  outputFileTracingRoot: path.join(__dirname, "../../"),
  env: {
    NEXT_PUBLIC_API_BASE_URL:
      process.env.NEXT_PUBLIC_API_BASE_URL || "http://localhost:4001",
  },
};
export default nextConfig;
```

**① `transpilePackages: ["@autix/contracts"]`**

Next 默认只编译自己项目目录内的代码，`node_modules` 里的东西一般跳过。而 contracts 的 `exports` 直接指向 `.ts` 源码，Next 就必须把它一起编译，否则会报 "Unexpected token 'export'" 之类的语法错误（`transpilePackages` 就是"把这些包加入编译"的白名单）。

**② `output: "standalone"`**

让 `next build` 产出一个**自包含**的运行目录（把运行所需的 node_modules 精简后复制到 `.next/standalone`）。它是为 Docker 部署准备的，2.8 起 Compose 会用到；本章 dev 模式不受影响。

**③ `outputFileTracingRoot: path.join(__dirname, "../../")`**

`standalone` 构建时，Next 要扫描并计算哪些文件需要复制进产物。在 monorepo 里，项目根不是仓库根，Next 默认只在项目目录里找，会漏掉仓库根/兄弟包里的文件。把它指到仓库根（`../../`），告诉 Next"文件追踪从仓库根开始"。

**④ `env: { NEXT_PUBLIC_API_BASE_URL }`**

这是本章前后端联通的"地址牌"：

- `process.env.NEXT_PUBLIC_API_BASE_URL` 优先（你在 shell 里怎么设都行）；
- 没设就用默认 `http://localhost:4001`。

为什么必须用 `NEXT_PUBLIC_` 前缀、为什么写在 next.config 里？见 §8.6。

### 8.5 `src/app/page.tsx`：一个客户端组件的完整解释

```tsx
"use client";
import { useState } from "react";
import { APP_NAME } from "@autix/contracts";

export default function Home() {
  const [result, setResult] = useState<string>("");

  async function callApi() {
    const res = await fetch(`${process.env.NEXT_PUBLIC_API_BASE_URL}/hello`);
    const data = await res.json();
    setResult(data.message);
  }

  return (
    <main style={{ padding: 24 }}>
      <h1>{APP_NAME}</h1>
      <button onClick={callApi}>调用 API</button>
      <pre style={{ marginTop: 16 }}>{result}</pre>
    </main>
  );
}
```

逐行解释：

- `"use client"`：Next App Router 默认是**服务端组件**（在服务器渲染、不能 useState/onClick）。加了这个指令，这个组件才会被打包成**客户端组件**，在浏览器执行交互逻辑。
- `useState`：保存 API 返回的 message，改变时触发 React 重渲染。
- `import { APP_NAME } from "@autix/contracts"`：**编译期**把这个常量内联进前端 bundle。这里能看到 `APP_NAME` 显示为 `llm`，说明"共享包"在编译期生效了。
- `fetch(...)`：在浏览器里发请求。注意 URL 是**绝对地址** `http://localhost:4001/hello`（不是 `/hello`），因为前端在 3002、后端在 4001。
- `res.json()` → `setResult(data.message)`：拿到 `{ message: "..." }`，把 message 存进 state。
- `<pre>{result}</pre>`：state 变了，React 重渲染，页面上出现文字。

### 8.6 `NEXT_PUBLIC_*` 的原理（浏览器为什么能拿到）

前端代码会打包成 JS 文件，由浏览器下载执行。**浏览器里没有 `process.env`**，也拿不到服务器上的环境变量——所以 Next 采用"**构建时替换**"：

- 构建（`next dev` / `next build`）时，Next 扫描代码里所有 `process.env.NEXT_PUBLIC_XXX`；
- 把 `NEXT_PUBLIC_` 开头的变量**在打包产物里替换成字面量字符串**；
- 于是浏览器运行到的代码里已经不是环境变量，而是写死的 `"http://localhost:4001"`。

推论：

- 必须 `NEXT_PUBLIC_` 前缀，否则浏览器端代码里仍然是 `undefined`；
- **改这个值需要重启 dev / 重新 build**（因为它已经写进产物了）；
- 生产环境要在 build 时注入（CI 环境变量），而不是运行时。

`next.config.ts` 的 `env` 字段就是"构建时注入"的一种方式；教程 2.8 会把它升级成"配置文件/环境驱动"。

### 8.7 跨域（CORS）到底是怎么回事

浏览器有**同源策略**：协议 + 域名 + 端口，三者任一不同就算跨域。

- 前端：`http://localhost:3002`
- 后端：`http://localhost:4001`
- 端口不同 → 跨域。

跨域的限制是"**浏览器**限制 JS 读取响应"，不是"服务器拒绝请求"。服务器默认可以收到请求，但浏览器会检查响应头里有没有 `Access-Control-Allow-Origin`，没有就不把结果交给 JS（控制台报 CORS 错误）。

所以解决方式是让**服务器授权**：

```ts
app.enableCors({
  origin: process.env.CORS_ORIGIN || "http://localhost:3002",
});
```

Nest（底层是 Express 的 cors 中间件）会在响应里加上：

```
Access-Control-Allow-Origin: http://localhost:3002
```

浏览器看到"这个源被允许"，才把 JSON 交给页面。简单 GET 请求不会预检（preflight）；以后带自定义头/非简单方法的 POST 会先发 `OPTIONS` 预检，Nest 的 CORS 配置也会一并处理。

替代方案 B（Next rewrites）：让浏览器请求同源的 `/api/*`，由 Next 服务器代理到 4001。浏览器看到的始终是同源 3002，不触发 CORS。两种方案二选一：A 简单直接，B 适合"对外只暴露一个域名"的部署。

> 小差异：教程的 `main.ts` 还带了 `credentials: true`，你的版本只保留了 `origin`。对当前这种简单 GET 没影响；以后要带 Cookie 时，需要恢复 `credentials: true`，并且前端 `fetch` 也要加 `credentials: "include"`。

### 8.8 `wait-on` 与启动顺序

`wait-on tcp:4001` 的原理：不断尝试建立 TCP 连接，直到 4001 可连接（或超时）。它解决的是"两个进程同时启动，前端比后端快"的竞态：

- 没有 wait-on：web 先起，用户点按钮时后端还没编译完 → 请求失败；
- 有 wait-on：web 会卡在 `wait-on` 这一步，等后端 listen 成功后才启动 Next。

代价是：如果后端一直起不来（比如 CLI 崩了），前端就会一直卡着不启动——所以看到"web 没反应"时，先看后端日志。

## 9. `services/chat`：NestJS 后端逐项讲解

### 9.1 Nest 启动时发生了什么

`main.ts` 里的 `NestFactory.create(AppModule)` 会：

1. 加载 `AppModule`；
2. 扫描 `controllers: [AppController]`、`providers: [AppService]`；
3. 用**依赖注入容器**实例化这些类（`AppController` 的构造器需要 `AppService`，Nest 自动注入）；
4. 根据装饰器（`@Controller()`、`@Get()`）注册路由；
5. `app.listen(4001)` 开始监听 HTTP 请求。

装饰器是"声明式配置"：`@Get('hello')` 就是"把这个方法注册成 GET /hello 的处理函数"。Nest 再把它交给 Express 路由表。

### 9.2 五个源码文件

**`src/main.ts`**

```ts
import 'reflect-metadata';
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.enableCors({ origin: process.env.CORS_ORIGIN || 'http://localhost:3002' });

  const port = process.env.PORT ?? 4001;
  await app.listen(port);
  console.log(`Chat service running on http://localhost:${port}`);
}
bootstrap();
```

- `import 'reflect-metadata'` 必须最早执行（装饰器元数据的基础设施）；
- `enableCors` 见 §8.7；
- 端口优先读环境变量 `PORT`（Docker 部署时用），默认 4001。

**`src/app.module.ts`**

```ts
@Module({
  imports: [],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}
```

根模块：声明"有哪些控制器、有哪些可注入的服务"。

**`src/app.controller.ts`**

```ts
@Controller()
export class AppController {
  constructor(private readonly appService: AppService) {}

  @Get('health')
  getHealth() {
    return this.appService.getHealth();
  }

  @Get('hello')
  getHello() {
    return this.appService.getHello();
  }
}
```

- `@Controller()` 不带路径前缀，所以 `@Get('health')` → `GET /health`；`@Get('hello')` → `GET /hello`；
- 构造器注入 `AppService`（Nest 负责实例化并传入）；
- `/health` 是健康探针，2.8 的 Compose 会用它判断容器是否就绪。

**`src/app.service.ts`**

```ts
@Injectable()
export class AppService {
  getHello(): { message: string } {
    return { message: `Hello from Chat, shared APP_NAME=${APP_NAME}` };
  }

  getHealth(): { ok: boolean } {
    return { ok: true };
  }
}
```

- `@Injectable()`：声明这个类可以被容器注入；
- `APP_NAME` 来自 `@autix/contracts`——**这个字符串没有写在服务端代码里**，而是从共享包来的。这是"共享契约"的后端侧验证。

**`src/app.module.ts` / 测试文件**：CLI 12 模板还生成了 `app.controller.spec.ts`、`test/app.e2e-spec.ts`、`jest.config.ts` 等测试脚手架，本章没用到，但 `tsconfig.json` 的 `types: ["node","jest"]` 依赖它们存在。

### 9.3 `nest-cli.json` 与 `tsconfig.build.json`

- `nest-cli.json`：`sourceRoot: "src"` 告诉 CLI 源码在哪；`deleteOutDir: true` 让每次 build 先清空 `dist`；`collection` 指向 schematics（`nest generate` 用）。
- `tsconfig.build.json`：见 §7.5。

### 9.4 `dev` / `build` / `start` 三个脚本的区别

| 脚本 | 命令（改造后） | 作用 |
| --- | --- | --- |
| `dev` | `bun node_modules/.bin/nest start --watch` | 编译（tsc watch）+ 启动 + 改代码自动重启 |
| `build` | `rm -rf dist tsconfig.tsbuildinfo && bun node_modules/.bin/nest build` | 清空旧产物，编译到 `dist/` |
| `start` | `bun run dist/main.js` | 直接运行编译产物（生产/部署用） |

`nest start --watch` 背后是：TypeScript 编译 → 输出 `dist/` → 启动 `node dist/main.js` → 监听文件变化 → 重新编译并重启。所以它同时是"编译器 + 进程管理器"。

### 9.5 端口与 CORS 的约定

- 4001：后端端口（`main.ts` 默认值，教程约定）；
- 3002：前端端口（`next dev --port 3002`）；
- 3002 在前端 CORS 白名单里（`enableCors`），两者必须一致，否则浏览器会拦。

## 10. 为什么"用 Bun"还会遇到 Node（本次最大的坑，原理全解）

### 10.1 Bun 的四张面孔

| 角色 | 命令示例 | 说明 |
| --- | --- | --- |
| 包管理器 | `bun install` | 装依赖、维护 `bun.lock` |
| 脚本运行器 | `bun run dev` | 执行 package.json 里的脚本 |
| JS/TS 运行时 | `bun src/index.ts` | 直接跑代码（替代 node） |
| 包执行器 | `bunx @nestjs/cli ...` | 类似 `npx`，临时下载并执行包 |

"这个项目用 Bun"通常只指前两者。**第三条（运行时）是否也换成 Bun，取决于命令怎么被调用。**

### 10.2 关键规则：`bun run` / `bunx` 会尊重 bin 的 shebang

npm 包的 `package.json` 里可以声明 `bin` 可执行文件，比如 Nest CLI 的 `bin/nest.js`，文件第一行是：

```js
#!/usr/bin/env node
```

当你在脚本里写 `nest start --watch`：

1. `bun run dev` 执行脚本，PATH 里找到 `node_modules/.bin/nest`；
2. `.bin/nest` 指向 `@nestjs/cli/bin/nest.js`；
3. Bun 看到 shebang 是 `node`，于是**用 Node 来执行它**，而不是 Bun。

`bunx` 同理：默认用 Node 运行包的可执行文件；只有加 `--bun` 才强制改用 Bun（`bunx --bun nest ...`）。

所以：**Next、Nest CLI 本身都是 Node 程序；教程写"用 Bun"，只是说安装/跑脚本用 Bun，CLI 内部还是 Node。**

### 10.3 事故现场还原：`ERR_REQUIRE_CYCLE_MODULE`

你执行 `bunx @nestjs/cli new services/chat` 时（2.6.1），得到：

```
Error [ERR_REQUIRE_CYCLE_MODULE]: Cannot require() ES Module
  .../ora/index.js in a cycle
  (from .../@angular-devkit/schematics/tasks/package-manager/executor.js)
Node.js v22.14.0
```

链条是这样的：

1. 教程里的命令没锁版本，今天 `bunx` 拉到 `@nestjs/cli` **12.0.11**（教程写作时 latest 是 11，它自己的 package.json 也写 `^11.0.0`）；
2. CLI 12 依赖 Angular devkit 22，其中 `executor.js` 是 CJS 代码，里面 `require("ora")`；
3. 而 CLI 12 用的 `ora` 是 **9.x 纯 ESM 包**；
4. 你的 Node 是 **22.14**，它默认开启 `require(esm)`，但在"循环依赖"场景会抛 `ERR_REQUIRE_CYCLE_MODULE`；
5. 于是 CLI **一启动就崩**，生成/构建/启动任何 nest 子命令都过不去。

补充验证（我们实测过）：用 Node 执行 `nest.js --version` 必崩；用 Bun 执行同一个文件正常打印 12.0.11。所以问题不在你的项目，而在"CLI 12 + Node 22.14"这个组合。

### 10.4 我们为什么把 `dev`/`build` 改成 `bun node_modules/.bin/nest ...`

既然 Bun 能正常跑这个 CLI，我们就让脚本显式用 Bun 跑它：

```json
"dev": "bun node_modules/.bin/nest start --watch",
"build": "rm -rf dist tsconfig.tsbuildinfo && bun node_modules/.bin/nest build"
```

- `bun node_modules/.bin/nest`：直接让 Bun 执行 `.bin/nest` 指向的 JS，绕过 shebang 的 Node 选择；
- CLI 自己的编译/调度逻辑跑在 Bun 上（Bun 的模块系统能处理这个 ESM/CJS 场景）；
- `nest start` 内部启动应用子进程时，跑的是**编译后的 `dist/main.js`**（普通 CJS，不包含出问题的 devkit 依赖），用 Node 或 Bun 都行。

这是"**运行时选择**"层面的修复，不改变任何业务代码，也不改变教程语义。

### 10.5 教程的版本漂移 & 它没写的 Node 前提

我们把教程翻了一遍，发现两件事：

1. **教程从没写 Node 的安装/版本要求**（全文只出现 `@types/node`、`node:path`、Dockerfile 里的 `node`）。它默认你机器上已经有可用的 Node——这是隐含前提。
2. **教程里的版本是"写作时的最新版"**：
   - `packageManager: "bun@1.3.11"`（你实际 1.4.4）；
   - `bunx @nestjs/cli new ...` 不锁版本（今天拉到 12，教程目标却是 11）；
   - Next 16.2.3（你实际 16.4.5）、React/依赖全套更新。

所以：**原文的流程在它写作时的版本组合下能跑通；今天照抄，就会踩到"未锁版本 + 时间漂移"的坑。** 这不是你操作错，也不是教程完全错，而是"教程只在一个时间点成立"。

以后照教程做时的建议：

- 先对齐大版本：Bun（packageManager 字段）、Node（LTS）、框架（Next/Nest）、CLI（教程 package.json 里的版本）；
- 凡是 `bunx`/`npx` 拉的 CLI，**优先锁版本**（`bunx --bun @nestjs/cli@11 ...`），或装进 devDependencies 用本地版本；
- 遇到玄学错误，先确认"这条命令到底跑在哪个 runtime、哪个版本"。

### 10.6 备选修法（了解即可）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A（本次采用） | 保留 Nest 12 / CLI 12，`dev`/`build` 用 Bun 跑 CLI | 与教程版本栈不完全一致 |
| B（贴教程） | 替换 `services/chat/package.json` 为 Nest 11 + `@nestjs/cli ^11` + `@nestjs/schematics ^11` + `typescript ^5.7`，`tsconfig` 改回 `commonjs`、去掉 `types:["node","jest"]`，`bun install` | 改动多，需重装 |
| C（不要做） | 降 Node 20 / 升 Node 24 | Node 20 不支持 `require(esm)`（会换一种错），Node 24 也有同类循环问题，治标不治本 |

CLI 11 的安全原因：它依赖 Angular devkit 19 + `ora` 5.4.1（CJS），在 Node 22 下不会触发这个 ESM 循环问题——所以教程的 `^11` 是"可跑"的关键之一。

### 10.7 怎么快速判断一条命令跑在哪个 runtime

- 看 `.bin` 脚本的 shebang：`head -1 node_modules/.bin/nest` → `#!/usr/bin/env node`；
- 想强制 Bun：`bunx --bun <pkg>`、`bun --bun <file>`；
- 想强制 Node：直接用 `node <file>`；
- 遇到"版本相关"的怪错，先 `node --version`、`bun --version`、`bunx <pkg> --version` 三个都看一眼。

## 11. 一次 `bun run dev` 的完整时序

```
你的终端
└─ bun run dev
   ├─ 1. bun run clean:ports
   │     └─ lsof 找到 3002/4001 的进程 → kill -9 → 端口清空
   └─ 2. turbo run dev --parallel --filter=@autix/chat --filter=@autix/chat-web
         ├─ Turbo 读根 package.json（workspaces、packageManager）+ bun.lock
         ├─ Turbo 读 turbo.json（tasks.dev: persistent, cache:false）
         ├─ 解析 filter → 命中两个包
         └─ 并行执行两个包的 scripts.dev
            ├─ @autix/chat  → bun node_modules/.bin/nest start --watch
            │    ├─ Nest CLI（跑在 Bun 上）用 tsc watch 编译 src → dist
            │    ├─ 启动 node dist/main.js → NestFactory → listen :4001
            │    └─ 改代码 → 重新编译 → 自动重启
            └─ @autix/chat-web → wait-on tcp:4001 && next dev --port 3002
                 ├─ wait-on 轮询 :4001，直到可连接
                 └─ Next dev 启动（Turbopack），浏览器 http://localhost:3002
         └─ Ctrl+C：Turbo 收起两个 persistent 进程（一起退出）
```

关键顺序点：

- **clean:ports 必须最先**（否则端口冲突）；
- **两个包是并行的**，但 chat-web 内部用 `wait-on` 等 chat 就绪，所以实际效果是"后端先可用、前端后启动"；
- **turbo 只负责调度**，真正干活的是各包自己的 `dev` 脚本；
- 你看到的 `Tasks: 2 successful` 之类汇总，是 Turbo 对"脚本进程启动成功"的统计，不代表 dev 进程结束。

## 12. 点击"调用 API"之后发生了什么（前后端通信全链路）

```
┌─────────────────────────┐                      ┌─────────────────────────┐
│ 浏览器                   │                      │ NestJS 服务              │
│ http://localhost:3002   │                      │ http://localhost:4001   │
│                         │                      │                         │
│ ① 点击"调用 API"          │                      │                         │
│ ② fetch(                 │  GET /hello          │                         │
│   "http://localhost:4001/hello") ──────────────> │ ③ Express 路由匹配        │
│    Origin: localhost:3002│                      │    AppController.getHello│
│                         │                      │ ④ AppService.getHello()  │
│                         │                      │    → APP_NAME = "llm"    │
│ ⑥ setResult(message)    │ <──────────────────── │ ⑤ 返回 JSON              │
│    页面 <pre> 出现文字     │  200 + CORS 响应头     │    {message: "..."}     │
└─────────────────────────┘                      └─────────────────────────┘
```

按层解释：

1. **触发**：`"use client"` 组件里的按钮 `onClick={callApi}` 在浏览器执行；
2. **发请求**：`fetch` 使用构建期注入的绝对地址 `http://localhost:4001/hello`（不是相对路径！）。浏览器自动带上 `Origin: http://localhost:3002`；
3. **路由**：Nest 把 `GET /hello` 映射到 `AppController.getHello`（`@Controller()` + `@Get('hello')`）；
4. **业务**：`AppService.getHello()` 拼出 `Hello from Chat, shared APP_NAME=llm`，其中 `APP_NAME` 来自 `@autix/contracts`；
5. **响应**：Nest 自动把返回对象序列化成 JSON；CORS 中间件补上 `Access-Control-Allow-Origin: http://localhost:3002`；
6. **渲染**：浏览器把 JSON 交给 JS（因为有 CORS 头），`data.message` 进入 state，React 重渲染，`<pre>` 里出现文字。

这条链路同时验证了四件事：

- **共享包**：前后端都引用了 `APP_NAME`；
- **进程通信**：浏览器用 HTTP 跨进程访问后端；
- **CORS**：服务器授权了 3002 这个源；
- **构建期注入**：环境变量被正确内联进前端产物。

两个常见误解：

- "前端 import 了 contracts，是不是可以直接调用后端函数？"——不是。**共享包是编译期共享，前后端运行时仍然进程隔离**，只能通过 HTTP 通信。
- "为什么不用 `/hello` 相对路径？"——相对路径会请求 3002（Next 服务器），不是 4001。除非在 Next 里配置 rewrite 代理（方案 B），才能用相对路径。

## 13. 踩坑总档案

| # | 现象 | 本质 | 我们的修法 / 现状 |
| --- | --- | --- | --- |
| 1 | `bun run dev` 报 `No package found with name '@autix/chat'` | Turbo `--filter` 按包名精确匹配；当时服务包不存在、web 包名少作用域 | 统一 `@autix/*` 命名，`bun install`；后补 `@autix/chat` |
| 2 | `turbo.json: invalid JSON ... found the end of the file` | turbo.json 是 0 字节（没保存成功） | 保存合法 JSON + `$schema` |
| 3 | `No tasks were executed ... Tasks: 0 successful` | turbo.json 合法，但 scope 里没有包有对应脚本（当时只有 contracts 且无 scripts） | 理解这是"无事可做"；建包/加脚本后消失 |
| 4 | 根 `bun run lint` 报 `Could not find task` | turbo.json 没声明 `lint` 任务 | 已知待办：需要时给 turbo.json 加 `"lint": {}` |
| 5 | `nest start` / `nest new` 报 `ERR_REQUIRE_CYCLE_MODULE` | CLI 12（devkit 22 + ESM ora）在 Node 22.14 的 require(esm) 循环检测下崩溃 | dev/build 改用 `bun node_modules/.bin/nest ...` |
| 6 | `wait-on` 卡住、前端不启动 | 后端没起来（端口不对/CLI 崩/编译失败） | 先单跑 `bun run dev:chat` 看日志 |
| 7 | 2.5.4 就跑根 `bun run dev` 必报错 | 教程顺序 bug：`@autix/chat` 到 2.6.1 才创建 | 建服务后再跑根 dev，或先单跑 `dev:chat-web` |
| 8 | 改了 `APP_NAME` 前端没变 | Next 需要重启 dev（或等热更新）；生产要重新 build | 重启 `next dev`；后端 watch 会自动重启 |
| 9 | 端口被占用（3002/4001 in use） | 上次进程没退干净 | `clean:ports` 或手动 `lsof -ti :端口 \| xargs kill -9` |
| 10 | 包改名/加依赖后 Turbo 仍找不到包 | 软链/锁文件还是旧的 | 重新 `bun install` |
| 11 | 想在 `package.json` 写注释，turbo 报解析失败 | Turbo 用严格 JSON 解析根 package.json | 注释写进 README/讲义（本文件） |

bun install

ls node_modules/.bun | head         # 依赖实体

## 附录 B：术语表

| 术语 | 含义 |
| --- | --- |
| monorepo | 一个仓库管理多个相互关联的包 |
| workspace | 仓库内被统一管理的独立包（有自己的 package.json） |
| hoisted / isolated | 依赖安装布局：平铺到根 / 严格按包隔离（本仓库） |
| 幽灵依赖 | 没在 package.json 声明、却能 require 到的包（hoisted 下常见） |
| Turborepo | monorepo 任务编排器：依赖图调度、并行、缓存 |
| `--filter` | Turbo 按包名筛选任务目标 |
| `persistent` | Turbo 任务标记：长期运行的进程（如 dev server） |
| CORS | 服务器的跨域授权机制（响应头 + 浏览器检查） |
| 预检 preflight | 跨域复杂请求前浏览器发的 OPTIONS 探测请求 |
| SSR / 服务端组件 | 默认在服务器渲染的 React 组件（不能用浏览器 API） |
| 客户端组件 | 加 `"use client"` 后打包到浏览器执行的组件 |
| DI / 依赖注入 | 容器按构造器参数自动创建并注入依赖（Nest 核心） |
| 装饰器元数据 | TS 编译时发射的类型信息，Nest 靠它做 DI |
| standalone | Next 产出的自包含运行目录（Docker 用） |
| inlining | 构建期把 `process.env.NEXT_PUBLIC_*` 替换成字面量 |
